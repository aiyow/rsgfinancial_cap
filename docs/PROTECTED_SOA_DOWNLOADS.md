# Protected resident SOA downloads

The resident's **Download protected SOA** action creates an AES-256 revision 6 encrypted PDF. The existing glass viewer is unchanged. A 24-character random opening password is sent to the current verified account email. An independent 64-character owner password is discarded. Neither password is returned to the browser or saved in the database, Activity Log, filenames, process arguments, or temporary files.

## Deploy in this order

1. For a new environment, keep `SOA_PROTECTED_EXPORTS_ENABLED=false` until its checks pass. Back up the database as usual. Apply only migration 043 with `npm run soa-exports:migrate` using the deployment database configuration. It creates operational tables and indexes; it does not modify statements, accounts, or existing audit history. The normal database initializer also discovers this migration for new installations.
2. Build/deploy `backend/Dockerfile` for linux/amd64 (Render's architecture). Render's API service now uses Docker; the frontend remains a static Vite site. The image pins Node 22.23.4 and its image digest, PDFKit 0.20.2 (lockfile), qpdf 12.4.2 (official binary bundle with verified release SHA256 and bundled runtime libraries), and bundled OFL Noto Sans fonts. The API runs as the non-root `node` user. Do not copy `.env`, local tools, or uploaded files into the image.
3. Preserve the working database, JWT, Cloudinary, client URL and SMTP settings on the API service. SMTP must support authenticated TLS with a valid certificate: implicit TLS on 465 (`SMTP_SECURE=true`) or required STARTTLS on 587 (`false`). TLS certificate verification and TLS 1.2 minimum are mandatory. **The repository blueprint declares Render Free; verify this matches the actual deployed service before syncing.** Render documents outbound SMTP 465/587 restrictions on Free instances; a working deployed mail service must be assessed using its actual configuration. Preserve any existing SMTP-capable instance rather than downgrading it. See [Render's Free service limits](https://render.com/docs/free). Port 25 is blocked on all Render services. The export flag is now enabled at the user's request; the API still fails closed if its checks do not pass. No hosting purchase or deployment was performed.
4. Configure `TRUST_PROXY_HOPS` only for the actual known reverse-proxy topology. With no setting the API uses the socket peer address, which conservatively shares one quota behind a proxy. Never accept arbitrary client `X-Forwarded-For` headers. Optional `SOA_EXPORT_RATE_SECRET` separates IP HMAC identifiers from `JWT_SECRET`.
5. Inside the deployed image run `npm run soa-exports:preflight`. It verifies migration availability, fonts/logo rendering, a required opening password, AES-256 R6 encryption, and authenticated TLS SMTP negotiation. It sends **no email**. Missing prerequisites produce a generic failure and keep downloads unavailable.
6. Complete the staging checks below, then explicitly set `SOA_PROTECTED_EXPORTS_ENABLED=true`. Startup and the first request run the same capability preflight. Missing configuration never restores the former unencrypted Print/PDF action. Disable the flag to stop new exports **and** file releases.

Local Windows development: install qpdf 12.4.2 and set `QPDF_PATH` to the absolute executable path. The portable binary used for validation is intentionally ignored under `backend/.tools/`; it is not a deployable dependency. The container supplies qpdf itself.

## API and lifecycle

- `POST /api/bills/:id/protected-exports`: existing resident bearer session, UUID `Idempotency-Key` header, empty body. Never accepts a recipient, PDF, totals, or template from the browser. Returns export ID, reference, state, filename, masked email and retrieval deadline; never the password.
- `GET /api/soa-exports/:exportId`: authenticated owner-only state. In-progress duplicate POSTs return 202 and the same export. The initial POST waits for rendering and SMTP; network retries must preserve the key. A failed/expired operation requires a new key.
- `GET /api/soa-exports/:exportId/file`: authenticated owner-only attachment, `private, no-store`, `nosniff`. No public URL or URL token. Repeated downloads return identical bytes with no additional email.

Account eligibility, verified current email, active effective unit assignment, forwarded/closed period and published statement are checked server-side. A repeatable-read snapshot captures the document. Stable fingerprints include revision, publication timestamp, dates, payer name, visible charge and payment values, invoice references, template and logo identifier. File/status requests recheck access, email and fingerprint; changed statements require a fresh export. Payment/advance changes therefore also invalidate an old portal artifact. Historical downloaded PDFs remain historical documents.

Reservation and quota events commit together, using PostgreSQL advisory locks per resident and IP across API replicas. New-export limits are 5/resident/hour, 60 seconds between creations, and 20/trusted client IP/hour. Idempotent retries consume no additional quota and send no additional email. Failed new attempts still consume quota to prevent email/rendering abuse.

`PREPARING → EMAIL_PENDING → READY` releases bytes only after SMTP reports acceptance for the exact recipient. Acceptance means the mail server accepted delivery; it cannot guarantee inbox delivery. Rejections, timeouts, uncertain outcomes and rendering errors produce `FAILED` with no downloadable bytes. The resident can request a fresh PDF/password if delivery is lost. There is no password recovery table or secret-bearing durable email outbox.

READY files expire 15 minutes after SMTP acceptance. Every request enforces the deadline; minute-based maintenance removes expired encrypted bytes. Abandoned PREPARING/EMAIL_PENDING rows fail after five minutes. A restart never resumes password delivery because the password no longer exists. The same maintenance removes operational metadata after 30 days and hourly quota events after one hour. Audit history has its existing independent retention rules. Export endpoints are classified as excluded **download operations** in `auditCoverage.js`.

qpdf uses a private stdin pipe for its arguments/secrets. Seekable plaintext input is kept in a private application-owned temporary directory, with restrictive file permissions, and removed in `finally`. Stale application-owned job directories older than five minutes are removed at startup and during maintenance; active jobs are excluded. qpdf stderr and raw SMTP errors are never logged or exposed by export endpoints. Only encrypted bytes are persisted in PostgreSQL.

The server renderer mirrors the existing A4 landscape statement: logo, account/payment details, association and previous-cycle water dates, invoice references, category advances, penalties, payments, totals, signatures and notices. Noto Sans embeds Filipino/Latin Unicode names and the peso sign; custom templates using scripts outside its character coverage require a suitable licensed font before rollout. PDF printing is allowed after unlocking; permission flags are advisory.

## Acceptance and recovery

Run `npm run test:soa-exports` with `QPDF_PATH` set to test the actual encryption binary as well as isolated PostgreSQL HTTP flows. Without qpdf the actual binary test explicitly skips; it must pass in staging before activation. Tests use a private disposable database schema and intercepted SMTP, not live resident data or emails. Other relevant checks: the backend unit suite, SOA correction integration, targeted frontend ESLint, production build and `frontend/test/browser/protectedSoaDownloads.mjs` plus the existing resident privacy browser test.

Staging must exercise the final deployed SMTP provider and the download on supported desktop/mobile browsers. Confirm matching short references in the password email and filename; no attachment or financial balance in email; missing/wrong passwords rejected; correct password opens in Chrome/Edge and Adobe Acrobat; printing works; Unicode, long names, long invoice lists, current logo and totals match the portal. Test interrupted requests/restarts, cooldowns, SMTP rejection and uncertainty, ended assignments, changed/unverified email, deleted/unpublished/corrected statements and expiration. Check app/proxy/SMTP logging policies do not capture message bodies or authorization headers.

For lost email, use **Create a fresh PDF and password** after the cooldown. For approved legacy unverified accounts, **Send account verification link** uses the existing verification flow and preserves approval. For a changed statement/email or expired artifact, the browser offers a fresh export. Operational errors are generic; investigate configuration and state/failure codes without logging PDFs or passwords.

The 15-minute lifetime governs portal retrieval only. A downloaded file remains openable with its emailed password and cannot be remotely revoked or expired. Visible statements can be captured or printed by browser/OS tools; the glass effect is a viewing convenience, not access control or DRM.
